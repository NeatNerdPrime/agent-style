# Recommendation: make the tagged commit the release unit

## The recommendation

Build from **registry-first**, with one structural change: keep the GitHub Release human-created and keep tag-before-publish, and get the identity property by building *from* the tag rather than by creating the tag *from* the build. Concretely, `publish.yml` keeps its `release: published` trigger, pins both jobs' checkout to `${{ github.event.release.tag_name }}`, and gains a first `gate` job that fails closed unless four things hold: the `validate.yml` run for the tagged commit concluded `success`; the tag name matches all five version-carrying files; every file in both package payloads is byte-identical to its repo-root twin; and the version does not already appear in a committed `releases.json` ledger. Each built artifact carries a generated `data/release.json` recording schema version, version, build commit, and a blob-sourced sha256 per payload file, plus the alias relation that makes `docs/rule-pack.md` checkable without shipping it (it is `RULES.md` with a 341-byte preamble, generated by `scripts/build-compact.py` and already diff-guarded by the `rule-pack-parity` job). The wheel, sdist, tgz, and a loose `release.json` are attached to the Release, and those artifacts already contain exactly the vendorer set PLAN step 3 enumerates, so no bundle generator is written and no content is duplicated. Nothing changes for consumers: `anywhere-agents` keeps pinning `ref:` and fetching `docs/rule-pack-compact.md`, no source kind is added, no manifest field is added, and no pack axis is touched.

## Why this and not the alternatives

**Registry-first's two best primitives survive intact, and they start green.** Measured at HEAD on committed blobs: each payload is 38 tracked files, 74 of the 76 payload entries match a repo-root blob exactly, and the two exceptions are the two `tools.json` copies, which are the same blob as each other (`e03af716`). An identity check written today passes today, so a first failure means real drift rather than a design problem. The build record is the primitive that makes a git-ref pin and a registry artifact checkable against each other, and it costs no duplicated bytes.

**Three of registry-first's five fatal flaws trace to one decision, so one reversal removes all three.** Moving Release creation into the workflow would have killed `real-agent-smoke.yml`, which triggers on `release: published` (confirmed at the top of that file) and is the only per-release live-agent check: GitHub does not start workflow runs from events created with the default `GITHUB_TOKEN`, so the loss would be silent. The same decision discarded the `RELEASING.md:480` tag-before-publish safeguard and left the promised "gate on the same side of the immutability boundary" unimplemented, because the proposed job graph had no validation job in it while concrete step 10 deleted the human CI-green gate at `RELEASING.md:170`. Keeping `gh release create` in the maintainer's hands preserves the smoke trigger and the safeguard; pinning the checkout to the tag (ref-first's one clearly correct edit) delivers the identity property from the safe direction, since the artifact is then built from the tagged commit by construction.

**The remaining two flaws trace to the payload duplication, and registry-first named the fix in its own costs.** Adding `data/rule-pack.md` would have grown each payload by 91,304 bytes (verified: `docs/rule-pack.md` is 91,304 bytes, `RULES.md` is 90,963, delta 341) to close a 341-byte gap on a path that `anywhere-agents` no longer fetches, and the guard proposed for it was a no-op, because `build-compact.py` writes `docs/rule-pack.md`, three compact outputs, and two bundled `RULES.md` copies, never a payload `rule-pack.md`. Recording the alias relation as a field in `release.json` gets the same verifiability for zero bytes.

**The ledger stays; its CI network check goes.** A committed `releases.json` checked against live registries inside CI is stale the instant an upload lands, so it passes vacuously before the publish steps and fails by construction after them. The ledger keeps the two uses that are not self-invalidating: a `bump-version.py` precondition that refuses any version already present, and a gate assertion at publish time. Registry queries stay in a local `--check` run from the pre-release checklist, where a network flake is a human's problem rather than a red release.

**Ref-first is not the base, but three of its parts are load-bearing here.** Byte sourcing must be `git show <rev>:<path>`, verified on this machine: `core.autocrlf` is `true` at the global level (the repository sets no local override), and `RULES.md` hashes to `1bc464cc…` as a blob and `b2c1a3e7…` in the working tree. A manifest built the obvious way records a value no fresh Linux clone and no `raw.githubusercontent.com` fetch reproduces. The tag trigger stays off `validate.yml`, because a workflow-level tag trigger would re-run the network link-check against every external URL in every tracked `.md` on the critical path of cutting a tag. What is dropped from ref-first is its `release.json`-at-the-repo-root scheme, its `git archive` bundle, and its docs-only reuse guard, which compared a `null` against a version string and could never fire.

**Minimal-change contributes the trigger direction and three cheap wins, with its one dangerous edit corrected.** Its npm idempotency guard keyed on mere existence would have converted the pipeline's only mechanical tag-versus-version signal into a silent green: with `skip-existing: true` on PyPI and an existence check on npm, a forgotten bump ships nothing and reports success. The guard here is keyed on tag agreement first, existence second, and the mirror assertion is added to the PyPI job where `skip-existing` hides the same mistake today.

**The docs-only convention is kept, not retired.** Minimal-change's retirement depended on a rehearsal carve-out that can never fire, since both packaging files are on the mandatory five-file bump list and `bump-version.py` refuses to run unless all five agree, so the diff condition is always false at the moment it is evaluated. The convention also has a live purpose: `anywhere-agents` resolves refs through `git ls-remote`, which matches tags and branches only, so a docs-only tag is how a content-only change becomes pinnable without a dual-registry release. The fix is to make the rule mechanical, since it currently lives only in prose at `RELEASING.md:76` and in the `CHANGELOG.md:9` banner.

**Architecture check.** No closed decision is reopened. Axis 2 gains no registry source kind, so `anywhere-agents/scripts/packs/passive.py` and its raw-URL derivation are untouched. Round 2 compression layering is respected: sizing stays expressed through `source.path:`, with no `variant:` field and no passive-to-active conversion. The "trust rejected as a third axis" decision at `pack-architecture.md:968` is respected in the strict sense, and this must be stated plainly to avoid inheriting ref-first's central flaw: **`release.json` is a producer-side build record, not a consumer integrity mechanism.** It is served from the same host at the same ref as the files it hashes, so it proves nothing against a hostile upstream. Consumer trust stays exactly where the architecture put it, in `update_policy:` plus `pack-lock.json` carrying the resolved commit and per-file sha256.

**1. Root `LICENSE` (independent, hours).** Create `C:\Users\yuezh\PycharmProjects\agent-style\LICENSE` stating the CC-BY-4.0 (rule text) and MIT (code) split and pointing at `LICENSES/`. **2. `scripts/release-identity.py`, proven on the current tree before anything depends on it.** One script, three modes, all reading bytes through `git show <rev>:<path>`:

```bash
python scripts/release-identity.py --check-tree                 # push/PR mode
python scripts/release-identity.py --check-release v0.4.0       # publish-gate mode
python scripts/release-identity.py --emit --commit "$GITHUB_SHA"  # build mode
```

`--check-tree` asserts: every payload path equals its repo-root twin (`data/RULES.md` to `RULES.md`, `data/rule-pack-compact.md` to `docs/rule-pack-compact.md`, `data/NOTICE.md` to `NOTICE.md`, `data/agents/*` to `agents/*`, `data/skills/*` to `skills/*`, `data/LICENSES/*` to `LICENSES/*`); the two `tools.json` copies are byte-identical to each other; the five version-carrying files agree with one another; and `docs/rule-pack.md` equals its preamble plus `RULES.md` from the first `#` heading onward. `--check-release` adds tag agreement (`$TAG` minus `v` equals all five version strings, including the two `tools.json` mirrors that `verify-install.sh --version-only` does not read) and a ledger lookup. `--emit` writes `packages/pypi/agent_style/data/release.json` and `packages/npm/data/release.json`.

Add a `release-identity` job to `.github/workflows/validate.yml` running `--check-tree` only. Do not add a tag trigger to that workflow. Confirm green on `37a2ff3` before continuing.

**3. Harden `.github/workflows/publish.yml`.** Keep the `release: published` trigger, keep `workflow_dispatch`, keep `npm_only` (it is what rescued v0.3.6), and keep `skip-existing: true` on PyPI. Add a `tag` input for the dispatch path, a shared `env: TAG:`, and a `gate` job that both publish jobs list under `needs:`:

```yaml
env:
  TAG: ${{ github.event.release.tag_name || inputs.tag }}

jobs:
  gate:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          ref: ${{ github.event.release.tag_name || inputs.tag }}
          fetch-depth: 0
      - name: Tag must be annotated
        run: test "$(git cat-file -t "$TAG")" = tag
      - name: Payload identity, five-file equality, tag agreement, ledger
        run: python scripts/release-identity.py --check-release "$TAG"
      - name: Validate must be green for the tagged commit
        env:
          GH_TOKEN: ${{ github.token }}
        run: |
          set -euo pipefail
          sha="$(git rev-parse "$TAG^{commit}")"
          c="$(gh run list --repo "$GITHUB_REPOSITORY" --workflow validate.yml \
                --commit "$sha" --limit 1 --json conclusion --jq '.[0].conclusion // ""')"
          [ "$c" = success ] || { echo "FAIL: validate.yml not green for $sha (got '${c:-none}')" >&2; exit 1; }
```

Pin both existing jobs' `actions/checkout@v6` (currently bare at lines 39 and 59) to the same `ref:`. Add a version assertion before each upload, and replace the bare `npm publish` at line 72 with a guard keyed on tag agreement first:

```yaml
      - name: Publish to npm via OIDC trusted publishing
        working-directory: packages/npm
        run: |
          set -euo pipefail
          v="$(node -p "require('./package.json').version")"
          [ "v$v" = "$TAG" ] || { echo "FAIL: package.json $v != tag $TAG" >&2; exit 1; }
          if npm view "agent-style@$v" version >/dev/null 2>&1; then
            echo "agent-style@$v already published; idempotent skip"; exit 0
          fi
          npm publish --provenance --access public
```

## What this deliberately does not solve

- **Downstream forks.** Nothing here makes `wenhaochai/claude-plugins` or any other hand-excerpting copy track upstream, and its internal copies already disagree with each other. A build record helps a reuser who chooses to record one; it creates no pull.
- **The two burned version numbers.** 0.3.2 and 0.3.3 can never be filled on either registry. The ledger records the holes; it cannot close them.
- **Latency for `anywhere-agents`-mediated consumers.** `bootstrap/packs.yaml` pins `ref: v0.3.6` with `update_policy: auto`, and against a fixed tag `auto` fires never. Those consumers move when aa bumps its own pin in its own release, which this item does not shorten.
- **Consumer-side integrity against a hostile upstream.** Stated above and worth repeating: `release.json` is a build record. It detects a publisher who changed a file and forgot to regenerate, which is upstream CI's job, and it is worth nothing against an attacker who controls the ref.
- **PLAN step 5 (`EXTENSIONS.md` plus an issue template) and the extension platform.** Both stay under the stop condition the plan already recorded: written pilot agreement from the two extenders first, otherwise stop after a schema and a static page.
- **Adapter attribution changes.** `packages/pypi/agent_style/owned_file.py` already stamps a trailing `<!-- owned-by: agent-style; version: vX.Y.Z; sha256: … -->` line, and `SIGNATURE_RE` anchors on that trailing form. No header is added, no adapter body changes, and `release.json` never enters any `enable` or `disable` JSON output, so the `--cli-parity` gate across five install modes is untouched.
- **The v0.3.6 commit-metadata mismatch as a harm claim.** npm records `gitHead e3f1436` while the tag resolves to `7654b96`. Verified: `git diff --name-only` between them returns exactly one file, `.github/workflows/publish.yml`, which is in neither payload and on no pinnable path. The design prevents recurrence; the incident itself delivered identical bytes and should not be cited as consumer harm.

## Questions only the maintainer can answer

1. **Does v0.4.0 go out through OIDC, or by hand one last time?** The PyPI pending publisher has never been exercised: the workflow's single run skipped the `pypi` job. Configuring it at pypi.org requires the maintainer's account, and the first exercise lands on a release that is already prepared. The alternative is to hand-publish v0.4.0 with the gate and identity work merged but the trigger unused, then make v0.4.1 the first OIDC cut. Either is defensible; the choice is about how much risk belongs on the release that is next rather than on the one after it.
2. **Approve roughly $0.05 for the v0.3.6 backfill, and accept that it must run before the v0.4.0 cut?** `RELEASING.md`'s own dispatch policy puts anything above $0.01 behind explicit per-run approval. Declining is coherent: the alternative is to leave `/releases/latest` naming v0.3.5 from 2026-04-29 until v0.4.0 ships and corrects it, at the cost of never proving the idempotent-skip path on a real re-publish.
3. **Does `agent-style pin [--json]` ship in v0.4.0 at all?** The build record inside the artifact and attached to the Release is the primitive and costs nothing extra. A CLI surface on top of it is the half with thin evidence: of six observed reusers, none runs the engine, and exactly one (`ecylmz/academic-writing-skills`) invented a machine-readable upstream link for itself. Shipping the data only, and adding the subcommand when someone asks, is the reading consistent with the plan's own stop-condition discipline. Shipping it now is the reading consistent with item 2 being the one item that acts on observed behavior.

## Preserved dissent

Stated in the critics' terms, not resolved by the recommendation above.

- **On the consumer-facing half (registry-first critique).** "The adoption evidence for the consumer-facing half is thin, by the plan's own record… all six observed reusers copy rule text, none runs the engine." And on the file that was dropped: the payload growth "buys a path with no current consumer." If question 3 is answered "ship the CLI," this objection stands unanswered.
- **On the headline evidence (registry-first critique).** "The delivered bytes are identical; only the recorded commit id differs. The class of risk stands; this instance is metadata-only and does not support the weight placed on it."
- **On the value of a build record at all (ref-first critique).** "release.json buys no integrity over what the architecture already anchors on… Anything that can serve a consumer bad content at a ref serves a matching release.json alongside it… It detects only the case where the publisher updated a file and forgot to regenerate release.json, which is upstream-CI territory, not consumer-integrity territory." The same critique's counter-proposal: "If tag immutability is the actual worry, the architecture already expresses the fix: set `update_policy: locked` or `prompt` on the agent-style entry in `anywhere-agents/bootstrap/packs.yaml:21`, and sign the tags upstream. Both are available today, neither needs a schema."
- **On whether this answers item 2 (minimal-change critique).** "The proposal answers a different question than Item 2 and does not label the substitution… What remains is release-metadata hygiene plus a root LICENSE. That is a defensible smaller project, but the unit of consumption is unchanged, and the single deliverable that speaks directly to the stated motivation (a pin file recording the installed upstream ref and commit) is discarded." That charge applies here too if question 3 is answered "data only."
- **On the root LICENSE (minimal-change critique).** "licensee does not recognize a custom split statement as a license; it will report Other or NOASSERTION. That beats null in the sidebar and costs nothing, so keep the edit, but it does not produce a machine-readable split."
- **On idempotency guards generally (minimal-change critique).** "Green plus both-skipped is indistinguishable from a forgotten version bump." The tag-agreement keying is the answer to this, and the objection is worth keeping in view whenever a future guard is added: an existence check without a tag assertion converts the pipeline's only loud signal into a silent success.
- **On what a release ordering cannot enforce (minimal-change critique).** "The inversion means no publish without a Release; it does not mean no tag without a publish. `git tag -a vX.Y.Z && git push origin vX.Y.Z` still produces a pinnable ref with no package." True here as well; the ledger records such a ref, it does not prevent one, and that is the intended behavior given that the docs-only convention is retained.
